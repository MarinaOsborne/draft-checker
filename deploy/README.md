# Деплой Article Quality Checker на VibeCode

Это внутренний инструмент с бэкендом на Express: он парсит `.docx`, хранит
серверный счётчик прогонов и вызывает модель `gpt-4o` через **OpenAI API
напрямую**, не показывая ключ в браузере. Поэтому — в отличие от чисто
статических сайтов — приложению нужен постоянно работающий Node-процесс,
а не просто nginx со статикой.

## Что нужно один раз

- **Ключ VibeCode** (`vibe_api_…`) — в личном кабинете VibeCode, раздел «Ключи API».
  Нужен только этому скрипту, чтобы задеплоить сервер на платформу.
- **Ключ OpenAI** (`sk-…`) — в личном кабинете OpenAI, раздел «API keys».
  Кладётся в `.env` внутри архива и используется приложением в рантайме
  для вызова `/api/analyze`; в деплое сайта платформы не участвует.
- Активная подписка **BitrixGPT + Маркетплейс** на портале — без неё платформа не выдаёт серверы.
- **Node.js** (сборка сайта и упаковка зависимостей идут локально).

## Деплой

Ключи можно передать тремя способами (скрипт проверяет их в этом порядке):

1. **Уже экспортированные переменные окружения** (например, секреты CI) — `VIBE_KEY`, `OPENAI_API_KEY` (и опционально `ACCESS_PIN`).
2. **Файл `deploy/.env.deploy`** — самый удобный для повторных деплоев:
   ```bash
   cp deploy/.env.deploy.example deploy/.env.deploy
   $EDITOR deploy/.env.deploy   # впиши VIBE_KEY / OPENAI_API_KEY / ACCESS_PIN
   ```
   Файл в `.gitignore`, в репозиторий не попадает.
3. **Интерактивный запрос** — если какого-то ключа нет ни в окружении, ни в
   файле, скрипт сам спросит его через `read -s` (ввод не отображается на экране).

Во всех трёх случаях ключ не попадает ни в историю шелла (`.bash_history`),
ни в вывод `ps aux` как аргумент командной строки — в отличие от варианта
`VIBE_KEY=... bash deploy/deploy.sh`, который лучше не использовать.

Дальше просто:

```bash
bash deploy/deploy.sh
```

`ACCESS_PIN` необязателен — по умолчанию `2847` (как в ТЗ). `OPENAI_MODEL`
(по умолчанию `gpt-4o`) тоже можно переопределить.

Скрипт соберёт фронтенд (`npm run build`), поставит прод-зависимости сервера
в отдельный staging-каталог, положит секреты в `.env` **внутри архива**
(не в гит — секреты никогда не коммитятся), закодирует архив в base64 и
одним JSON-запросом создаст (или обновит) приложение на платформе. В конце
напечатает адрес вида `https://app-xxxxx.vibecode.bitrix24.tech`.

Запускай ту же команду при каждом обновлении сайта или при смене пина/ключа —
приложение переиспользуется (id хранится в `deploy/.vibe-server`, в гит не идёт).

## Как устроен деплой: Galaxy-контейнер, а не VM

Приложение деплоится как **Galaxy-контейнер** (общий хост), а не отдельная
VM — в `vibecoders-front-ui-gallery/deploy/deploy-galaxy.sh` это отдельный
сценарий, и наш `deploy/deploy.sh` следует ему же. Три особенности этого
режима, из-за которых скрипт несколько раз переписывался, пока не сработал:

1. **runtime нужен в каждом запросе деплоя** (и при создании, и при каждом
   обновлении) — иначе `GALAXY_DEPLOY_RUNTIME_REQUIRED`.
2. **готовность проверяется через `status=running`**, а не
   `blackholeStatus=CONNECTED` (тот статус Galaxy никогда не достигает).
3. **и создание, и (ре)деплой — один JSON-запрос** с исходниками в поле
   `source.content` как base64, а не multipart-загрузка файла. С
   multipart-запросом (`-F "archive=@..."`) платформа отвечала успехом,
   создавала app slot, но реального деплоя не запускала («No source was
   deployed — the app slot was created but a deploy never started»).

Если получишь ошибку про `runtime`/`image`, посмотри доступные варианты в
личном кабинете VibeCode (или спроси поддержку платформы) и поправь
`RUNTIME_IMAGE` в `deploy/deploy.sh`.

### Деплой «зависает» на шаге 3/5

Запрос с исходниками (JSON с base64 в теле) шлётся с тайм-аутом (4 минуты
на сам запрос) — без него зависшее соединение ждало бы ответа молча и
бесконечно (это уже случалось на раннем multipart-варианте скрипта).
Для **редеплоя на существующее приложение** тайм-аут не фатален — скрипт
предупредит и всё равно проверит готовность через опрос `status=running`,
т.к. сборка могла продолжиться на сервере в фоне.

Для **создания нового приложения** тайм-аут обрабатывается строже: скрипт
останавливается и просит сначала проверить в личном кабинете VibeCode, не
создалось ли приложение «article-quality-checker» несмотря на то, что ответ
до нас не дошёл — иначе слепой повтор может создать дубль.

Если скрипт пишет «Не дождался running за ~4 мин» (уже после успешного
запроса) — проверь вручную:

```bash
curl -H "X-Api-Key: $VIBE_KEY" https://vibecode.bitrix24.tech/v1/infra/servers/$(cat deploy/.vibe-server)
```

и посмотри `status`/`provisionError` в ответе. Если приложение застряло в
сломанном состоянии и продолжает падать — удали `deploy/.vibe-server` перед
повторным запуском, чтобы скрипт создал его заново.

## Локальная проверка перед деплоем

```bash
cp .env.example .env   # заполни ACCESS_PIN / OPENAI_API_KEY
npm install
npm run dev             # vite (5173) + express (3000) с прокси /api
```

или прод-сборка целиком:

```bash
npm run build
npm start                # обслуживает dist/ и /api на одном порту (3000)
```

## Если что-то пошло не так

- **«Приложение не создалось» / ошибка 402** — пополни баланс VibeCode или проверь подписку BitrixGPT + Маркетплейс.
- **502 от `/api/analyze`** — проверь, что `OPENAI_API_KEY` задан и валиден (в логах сервера будет видна причина от OpenAI: неверный ключ, нет доступа к модели, лимиты и т.п.).

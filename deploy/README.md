# Деплой Article Quality Checker на VibeCode

Это внутренний инструмент с бэкендом на Express: он парсит `.docx`, хранит
серверный счётчик прогонов и вызывает модель `bitrix/bitrixgpt-5.5` через
**AI Router платформы VibeCode**, не показывая ключ в браузере. Поэтому —
в отличие от чисто статических сайтов — приложению нужен постоянно
работающий Node-процесс, а не просто nginx со статикой.

## Что нужно один раз

- **Ключ VibeCode** (`vibe_api_…`) — в личном кабинете VibeCode, раздел «Ключи API».
  Это единственный ключ, который нужен приложению: он же деплоит сервер,
  он же (в рантайме) вызывает AI Router.
- Активная подписка **BitrixGPT + Маркетплейс** на портале — без неё платформа не выдаёт серверы.
- **Node.js** (сборка сайта и упаковка зависимостей идут локально).

## Деплой

Ключ можно передать тремя способами (скрипт проверяет их в этом порядке):

1. **Уже экспортированная переменная окружения** (например, секрет CI) — `VIBE_KEY` (и опционально `ACCESS_PIN`).
2. **Файл `deploy/.env.deploy`** — самый удобный для повторных деплоев:
   ```bash
   cp deploy/.env.deploy.example deploy/.env.deploy
   $EDITOR deploy/.env.deploy   # впиши VIBE_KEY / ACCESS_PIN
   ```
   Файл в `.gitignore`, в репозиторий не попадает.
3. **Интерактивный запрос** — если ключа нет ни в окружении, ни в файле,
   скрипт сам спросит его через `read -s` (ввод не отображается на экране).

Во всех трёх случаях ключ не попадает ни в историю шелла (`.bash_history`),
ни в вывод `ps aux` как аргумент командной строки — в отличие от варианта
`VIBE_KEY=... bash deploy/deploy.sh`, который лучше не использовать.

Дальше просто:

```bash
bash deploy/deploy.sh
```

`ACCESS_PIN` необязателен — по умолчанию `2847` (как в ТЗ). `VIBE_AI_MODEL`
(по умолчанию `bitrix/bitrixgpt-5.5`) и `VIBE_AI_BASE_URL` тоже можно
переопределить — см. предупреждение ниже.

Скрипт соберёт фронтенд (`npm run build`), поставит прод-зависимости сервера
в отдельный staging-каталог, положит секреты в `.env` **внутри архива**
(не в гит — секреты никогда не коммитятся), поднимет (или переиспользует)
сервер и зальёт архив. В конце напечатает адрес вида
`https://app-xxxxx.vibecode.bitrix24.tech`.

Запускай ту же команду при каждом обновлении сайта или при смене пина/ключа —
сервер переиспользуется (id хранится в `deploy/.vibe-server`, в гит не идёт).

## Рантайм: node20, и почему он нужен на каждый деплой

Готовый скрипт из `vibecoders-front-ui-gallery` рассчитан на чисто
статический сайт и всегда запрашивает `runtime=static` (образ с nginx).
Здесь вместо этого используется `runtime=node20`.

Такие приложения платформа деплоит как **Galaxy-контейнер** (общий хост),
а не отдельную VM — в `vibecoders-front-ui-gallery/deploy/deploy-galaxy.sh`
это отдельный сценарий. В Galaxy-режиме `runtime` нужно передавать в
**каждом** запросе деплоя — и при первом создании сервера, и при каждом
последующем обновлении, — иначе платформа отвечает ошибкой
`GALAXY_DEPLOY_RUNTIME_REQUIRED`. `deploy/deploy.sh` учитывает это: `-F
"runtime=$RUNTIME_IMAGE"` передаётся и в запросе создания, и в запросе
`/deploy`.

Если всё же получишь ошибку про `image`/`runtime`:

```bash
curl -H "X-Api-Key: $VIBE_KEY" \
  https://vibecode.bitrix24.tech/v1/infra/providers/bitrix-cloud/images
```

посмотри список доступных образов (или загляни в личном кабинете VibeCode /
спроси поддержку платформы) и поправь переменную `RUNTIME_IMAGE` в
`deploy/deploy.sh`. Если сервер уже был создан с неверным рантаймом и
продолжает падать — удали `deploy/.vibe-server` перед повторным запуском,
чтобы скрипт создал сервер заново, а не пытался обновить существующий.

### Деплой «зависает» на шаге 4/5

На Galaxy сам запрос заливки (`POST .../deploy`) не обязан сразу вернуть
готовый результат — сборка контейнера может продолжаться уже после ответа
(или ответ вовсе не дойдёт вовремя). Поэтому у этого запроса есть тайм-аут
(3 минуты), а реальная готовность в любом случае проверяется отдельно —
опросом `status=running` с точками прогресса, как и при создании сервера.
Если увидишь `⚠️ Запрос не дождался ответа за 3 мин` — это не обязательно
ошибка, просто жди опрос статуса дальше.

Если скрипт в итоге пишет «Не дождался status=running за ~6 мин» — проверь
вручную:

```bash
curl -H "X-Api-Key: $VIBE_KEY" https://vibecode.bitrix24.tech/v1/infra/servers/$(cat deploy/.vibe-server)
```

и посмотри `status`/`provisionError` в ответе.

## ⚠️ Непроверенное место: путь AI Router

Вызов модели в `server/lib/vibeAiClient.js` бьёт в
`https://vibecode.bitrix24.tech/v1/ai` как OpenAI-совместимый эндпоинт —
**это по-прежнему предположение**, не подтверждённое реальным запросом:
сессия, в которой собирался этот проект, не имела сетевого доступа к
`vibecode.bitrix24.tech` (заблокировано политикой песочницы).

Если после деплоя `/api/analyze` отдаёт 502 (или в логах сервера видно
404/401 от AI Router) — открой документацию по адресу
https://vibecode.bitrix24.tech/v1/me, найди реальный путь AI Router и формат
заголовка авторизации, и поправь `VIBE_AI_BASE_URL` (в `deploy/.env.deploy`
или прямо в `server/lib/vibeAiClient.js`, если заголовок авторизации тоже
отличается от `X-Api-Key`/`Bearer`).

## Локальная проверка перед деплоем

```bash
cp .env.example .env   # заполни ACCESS_PIN / VIBE_KEY
npm install
npm run dev             # vite (5173) + express (3000) с прокси /api
```

или прод-сборка целиком:

```bash
npm run build
npm start                # обслуживает dist/ и /api на одном порту (3000)
```

## Если что-то пошло не так

- **«Сервер не создался» / ошибка 402** — пополни баланс VibeCode или проверь подписку BitrixGPT + Маркетплейс.
- **Хочешь дешевле** — поменяй `PLAN` в `deploy/deploy.sh` на `bc-agent`, или включи авто-сон, заменив `"sleepAfterMinutes":null` на `"sleepAfterMinutes":60`.
- **502 от `/api/analyze`** — см. раздел про AI Router выше: скорее всего, дело в пути/авторизации роутера, а не в самом ключе.
